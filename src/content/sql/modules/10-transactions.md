## Транзакция

Группа команд, которая выполняется **целиком или никак**.

```sql
BEGIN;
UPDATE pizzeria SET rating = 5 WHERE name = 'Pizza Hut';
COMMIT;    -- зафиксировать; ROLLBACK — отменить всё с BEGIN
```

Без `BEGIN` каждая команда — отдельная транзакция с автоматическим `COMMIT` (autocommit).

### ACID

| Буква | Свойство | Что значит |
|---|---|---|
| A | Atomicity | все команды транзакции применяются вместе или ни одна |
| C | Consistency | после транзакции соблюдены все ограничения (PK, FK, CHECK) |
| I | Isolation | параллельные транзакции не мешают друг другу — степень задаёт **уровень изоляции** |
| D | Durability | после `COMMIT` данные переживут падение сервера (WAL) |

## Аномалии параллельного доступа

| Аномалия | Что происходит |
|---|---|
| **Dirty read** | читаем незафиксированные изменения чужой транзакции |
| **Lost update** | две транзакции читают одно значение, обе пишут — одна запись затирает другую |
| **Non-repeatable read** | повторный `SELECT` той же строки в одной транзакции даёт другое значение |
| **Phantom read** | повторный запрос по условию видит новые (или пропавшие) строки |
| **Serialization anomaly** | результат параллельного выполнения невозможен ни при каком последовательном порядке |

## Уровни изоляции в PostgreSQL

| Уровень | Dirty read | Non-repeatable | Phantom | Lost update |
|---|---|---|---|---|
| `READ UNCOMMITTED` | нет¹ | возможно | возможно | возможно |
| `READ COMMITTED` (по умолчанию) | нет | возможно | возможно | возможно |
| `REPEATABLE READ` | нет | нет | нет² | нет — ошибка |
| `SERIALIZABLE` | нет | нет | нет | нет — ошибка |

¹ В PostgreSQL `READ UNCOMMITTED` работает как `READ COMMITTED` — грязного чтения нет вообще.

² По стандарту SQL фантомы на `REPEATABLE READ` допустимы, но в PostgreSQL их нет: уровень построен на снимке данных.

```sql
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;
-- или
BEGIN;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;  -- до первого запроса
```

> Уровень задаётся **один раз**: либо в `BEGIN`, либо `SET TRANSACTION` сразу после него. Писать оба подряд (как в части файлов модуля) не ошибка, но избыточно.

## Как это устроено: MVCC и снимки

PostgreSQL не перезаписывает строку при `UPDATE`, а создаёт её новую версию. Каждая транзакция видит данные через **снимок** (snapshot) — набор версий, зафиксированных к определённому моменту.

| Уровень | Когда берётся снимок |
|---|---|
| `READ COMMITTED` | перед **каждым** запросом → видит всё, что закоммичено к этому моменту |
| `REPEATABLE READ`, `SERIALIZABLE` | перед **первым** запросом транзакции → весь мир «заморожен» |

Отсюда все наблюдения модуля:

- `READ COMMITTED`: повторный `SELECT` видит чужой `COMMIT` → non-repeatable read и phantom.
- `REPEATABLE READ`: повторный `SELECT` возвращает то же самое; новое значение видно только после своего `COMMIT`.
- Читатели не блокируют писателей, писатели не блокируют читателей. Блокируются только **два писателя одной строки**.

## Lost update: что делает второй UPDATE

Обе транзакции прочитали 4.6. Сеанс 1 сделал `UPDATE … = 4`, сеанс 2 — `UPDATE … = 3.6`. Второй `UPDATE` **ждёт**, пока строка заблокирована первым. После `COMMIT` сеанса 1:

| Уровень | Что делает ожидавший UPDATE | Итог |
|---|---|---|
| `READ COMMITTED` | перечитывает новую версию строки и применяет изменение | **3.6** — запись 4 потеряна |
| `REPEATABLE READ` | видит, что строку изменили после его снимка | `ERROR: could not serialize access due to concurrent update`, транзакция откатывается |

> Ошибка сериализации — штатная ситуация, а не баг. Приложение на `REPEATABLE READ` / `SERIALIZABLE` должно уметь **повторить транзакцию**.

На `READ COMMITTED` lost update предотвращают сами запросы:

- атомарный `UPDATE … SET rating = rating - 0.4` вместо «прочитал → посчитал → записал»;
- `SELECT … FOR UPDATE` — блокирует строку уже при чтении.

## Deadlock

Две транзакции ждут друг друга по кругу:

| Шаг | Сеанс 1 | Сеанс 2 |
|---|---|---|
| 1 | блокирует строку id = 1 | |
| 2 | | блокирует строку id = 2 |
| 3 | ждёт id = 2 | |
| 4 | | ждёт id = 1 → **цикл** |

PostgreSQL проверяет граф ожиданий (через `deadlock_timeout`, по умолчанию 1 с), находит цикл и откатывает одну транзакцию: `ERROR: deadlock detected`. Вторая продолжает работу.

Как избежать: **блокировать строки в одном и том же порядке** во всех транзакциях (например, по возрастанию `id`) и держать транзакции короткими.

## Поиск зависшей транзакции

```sql
SELECT pid, state, query, age(clock_timestamp(), query_start)
FROM pg_stat_activity
WHERE state != 'idle'
ORDER BY 4 DESC;

SELECT pg_cancel_backend(pid);     -- отменить текущий запрос
SELECT pg_terminate_backend(pid);  -- разорвать соединение целиком
```

Состояние `idle in transaction` — сессия открыла `BEGIN` и не закрыла: держит блокировки и мешает очистке старых версий строк (VACUUM).
