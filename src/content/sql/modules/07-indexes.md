## Что такое индекс

Индекс — отдельная структура данных, которая по значению колонки быстро находит нужные строки, не читая всю таблицу. По умолчанию в PostgreSQL это **B-Tree** — сбалансированное дерево: поиск за `O(log n)` вместо `O(n)` при полном просмотре.

Цена индекса:

- **Место на диске** — это копия значений колонки + ссылки на строки.
- **Медленнее запись** — каждый `INSERT`, `UPDATE`, `DELETE` обновляет и таблицу, и все её индексы.
- Индекс без запросов, которые им пользуются, — чистый убыток.

## Что индексируется автоматически

| Объект | Индекс создаётся сам? |
|---|---|
| `PRIMARY KEY` | да |
| `UNIQUE` | да |
| `FOREIGN KEY` (колонка, которая ссылается) | **нет** |

> Колонки внешних ключей (`menu.pizzeria_id`, `person_order.person_id` …) участвуют почти в каждом JOIN, но индекса на них нет, пока не создашь вручную. Это первое, что проверяют при оптимизации.

Имя по соглашению — `idx_<таблица>_<колонка>`:

```sql
DROP INDEX IF EXISTS idx_menu_pizzeria_id;
CREATE INDEX idx_menu_pizzeria_id ON menu(pizzeria_id);
```

`DROP INDEX IF EXISTS` перед `CREATE` делает скрипт **идемпотентным** — его можно запускать повторно.

## Типы индексов в модуле

| Тип | Пример | Когда нужен |
|---|---|---|
| обычный B-Tree | `ON menu(pizzeria_id)` | `=`, `<`, `>`, `BETWEEN`, `ORDER BY`, JOIN |
| функциональный | `ON person(UPPER(name))` | в `WHERE` стоит выражение, а не голая колонка |
| составной | `ON person_order(person_id, menu_id, order_date)` | фильтр по нескольким колонкам сразу |
| уникальный | `CREATE UNIQUE INDEX … (pizzeria_id, pizza_name)` | запрет дубликатов + быстрый поиск |
| частичный | `… WHERE order_date = '2022-01-01'` | индексируется только подмножество строк |

### Функциональный индекс

Используется, только если в запросе **то же самое выражение**:

```sql
CREATE INDEX idx_person_name ON person(UPPER(name));

SELECT * FROM person WHERE UPPER(name) = 'ANNA';  -- индекс работает
SELECT * FROM person WHERE name = 'Anna';         -- не работает
```

### Составной индекс: правило левого префикса

Индекс `(person_id, menu_id, order_date)` отсортирован сначала по `person_id`, внутри — по `menu_id`, потом по `order_date`. Как телефонный справочник: фамилия → имя.

| Условие в WHERE | Индекс полезен? |
|---|---|
| `person_id = 8` | да |
| `person_id = 8 AND menu_id = 19` | да |
| `menu_id = 19` | почти нет — первой колонки нет в условии |

Порядок колонок в индексе важен, порядок условий в `WHERE` — нет.

### Частичный индекс

```sql
CREATE UNIQUE INDEX idx_person_order_order_date
ON person_order(person_id, menu_id)
WHERE order_date = '2022-01-01';
```

- Меньше и быстрее полного: в нём только строки, подходящие под условие.
- Планировщик возьмёт его, только если `WHERE` запроса **включает** условие индекса.
- `UNIQUE` + `WHERE` — уникальность только внутри подмножества: «клиент не может заказать одну позицию дважды 01.01.2022».

## EXPLAIN и EXPLAIN ANALYZE

| Команда | Что делает |
|---|---|
| `EXPLAIN query` | показывает **план** и оценку стоимости, запрос не выполняет |
| `EXPLAIN ANALYZE query` | **выполняет** запрос и показывает реальное время и число строк |

> `EXPLAIN ANALYZE` на `UPDATE` / `DELETE` действительно меняет данные. Оборачивай в `BEGIN; … ROLLBACK;`.

Узлы плана, которые встречаются в модуле:

| Узел | Что происходит |
|---|---|
| `Seq Scan` | чтение всей таблицы подряд |
| `Index Scan` | поиск по индексу + чтение строки из таблицы |
| `Index Only Scan` | всё нужное есть в самом индексе — таблицу не читаем |
| `Bitmap Heap Scan` | собрать по индексу список страниц, прочитать их пачкой |

`Index Only Scan` возможен, когда все колонки из `SELECT` и `WHERE` есть в индексе (ex03, ex05).

### enable_seqscan = off

```sql
SET enable_seqscan = off;
```

Запрещает планировщику Seq Scan (точнее, делает его очень «дорогим») в **текущей сессии**. Нужен, чтобы проверить, что индекс вообще может использоваться. В рабочей системе не включают.

## Почему на маленьких таблицах индекс не помогает

Замеры из репозитория (PostgreSQL 16.13, таблицы по 6–20 строк, медиана 7 прогонов) для ex06:

| Вариант | Узлы плана | Время, мс |
|---|---|---|
| по умолчанию | Seq Scan `menu` + Seq Scan `pizzeria` | 0.188 |
| `enable_seqscan = off`, без `idx_1` | Index Only Scan + Index Scan | 0.242 |
| `enable_seqscan = off`, с `idx_1` | Index Only Scan + Index Only Scan | 0.275 |

Вся таблица из 20 строк помещается в одну страницу (8 КБ). Прочитать её целиком дешевле, чем пройти по дереву индекса и потом сходить в таблицу. Планировщик это знает и выбирает Seq Scan. Индексы окупаются на таблицах в тысячи страниц.

> Вывод для собеседования: «индекс есть, а план его не использует» — не всегда ошибка. Сначала смотри на объём данных и статистику (`ANALYZE table`).
