## Стенд из двух узлов

Две VM соединены внутренней сетью VirtualBox через `enp0s8`:

| Узел | Адрес на enp0s8 | Сеть |
|---|---|---|
| ws1 | `192.168.100.10/16` | `192.168.0.0/16` |
| ws2 | `172.24.116.8/12` | `172.16.0.0/12` |

Провод общий, но адреса из **разных сетей**. Без маршрута ws1 не знает, что `172.24.116.8` доступен через `enp0s8`, и шлёт пакет в маршрут по умолчанию — через `enp0s3` в NAT VirtualBox, где ws2 нет.

## Таблица маршрутизации

```bash
ip route        # или ip r
```

Для каждого пакета ядро ищет подходящий маршрут по адресу назначения:

| Тип маршрута | Пример | Откуда |
|---|---|---|
| connected | `192.168.0.0/16 dev enp0s8 proto kernel` | создаётся сам при назначении адреса |
| статический | `172.16.0.0/12 dev enp0s8` | добавлен вручную или в Netplan |
| по умолчанию | `default via 10.0.2.2 dev enp0s3` | шлюз для всего остального |

### Маршрут через интерфейс и через шлюз

```bash
ip route add 172.16.0.0/12 dev enp0s8                  # цель — в этом сегменте, отправлять напрямую
ip route add 10.20.0.0/26 via 10.100.0.12              # отправлять через роутер 10.100.0.12
```

- `dev` — «адресат прямо за этим интерфейсом»: ядро спросит его MAC через ARP.
- `via` — «отдай пакет этому роутеру»: ARP-запрос пойдёт за MAC роутера, а IP назначения в пакете останется прежним.
- Адрес в `via` должен быть **соседом** — из connected-сети.

## Временно и постоянно

| Способ | Команда | После reboot |
|---|---|---|
| временно | `sudo ip route add 172.16.0.0/12 dev enp0s8` | маршрут пропадёт |
| постоянно | раздел `routes:` в Netplan + `sudo netplan apply` | сохранится |
| удалить | `sudo ip route del 172.16.0.0/12` | — |

```yaml
# /etc/netplan/00-installer-config.yaml (ws1)
    enp0s8:
      dhcp4: no
      addresses:
        - 192.168.100.10/16
      routes:
        - to: 172.16.0.0/12
          via: 192.168.100.10
```

### Найденная ошибка: via на собственный адрес

В проекте `via` указывает на адрес **самого** ws1 (`192.168.100.10`), а на ws2 — на `172.24.116.8`. Это сработало — ping 0% loss после reboot, — но смысл записи неверный: шлюз — это **другой** узел, которому передаётся пакет. Ядро распознаёт свой адрес и фактически отправляет пакет напрямую с интерфейса.

Корректная запись, эквивалентная ручной команде `ip route add 172.16.0.0/12 dev enp0s8`:

```yaml
      routes:
        - to: 172.16.0.0/12
          scope: link
```

`scope: link` — «адресат доступен напрямую на этом линке, шлюз не нужен».

## Проверка пропускной способности: iperf3

```bash
iperf3 -s                    # на ws2 — сервер, слушает TCP 5201
iperf3 -c 172.24.116.8       # на ws1 — клиент, тест 10 секунд
```

Результат из проекта: **2.49 GB за 10 с, 2.14 Gbit/s sender / 2.13 Gbit/s receiver, 9557 retransmits.**

| Поле | Значение |
|---|---|
| `Transfer` | сколько данных передано |
| `Bitrate` | скорость; `sender` — отправлено, `receiver` — реально получено |
| `Retr` | повторные передачи TCP |

- Скорость больше 1 Gbit/s, потому что обе VM на одном хосте: трафик идёт через виртуальный коммутатор в памяти, физической сетевой карты на пути нет.
- Retransmits в виртуальной сети — обычно переполнение буферов виртуального коммутатора, а не потери в кабеле.

| Флаг | Значение |
|---|---|
| `-t 30` | тест 30 секунд |
| `-P 4` | 4 параллельных потока |
| `-R` | обратное направление (сервер → клиент) |
| `-u -b 100M` | UDP с заданной скоростью — измерить потери и джиттер |
