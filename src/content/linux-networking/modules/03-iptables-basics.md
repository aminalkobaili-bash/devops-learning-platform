## Таблицы и цепочки iptables

`iptables` управляет фильтром пакетов ядра Linux (netfilter). Правила сгруппированы в **таблицы**, а внутри — в **цепочки**, через которые проходит пакет.

| Таблица | Для чего |
|---|---|
| `filter` (по умолчанию) | пропустить или отбросить |
| `nat` | менять адреса и порты (модуль 06) |
| `mangle` | менять служебные поля пакета |

| Цепочка (filter) | Какие пакеты |
|---|---|
| `INPUT` | адресованы **этому** хосту |
| `OUTPUT` | созданы **этим** хостом |
| `FORWARD` | проходят **через** хост (роутер, модуль 06) |

## Правило

```bash
iptables -A INPUT -p tcp --dport 22 -j ACCEPT
```

| Часть | Значение |
|---|---|
| `-A INPUT` | добавить в **конец** цепочки INPUT (`-I` — в начало) |
| `-p tcp --dport 22` | условие: TCP на порт 22 |
| `-j ACCEPT` | действие (target) |

| Действие | Что делает |
|---|---|
| `ACCEPT` | пропустить |
| `DROP` | молча отбросить: отправитель ждёт до таймаута |
| `REJECT` | отбросить и сообщить отправителю (ICMP unreachable / TCP RST) |

## Первое совпадение

Пакет идёт по правилам цепочки **сверху вниз**. Первое правило, условие которого совпало, решает судьбу пакета — дальше правила не смотрятся. Если ничего не совпало — срабатывает **политика цепочки** (`-P`), по умолчанию `ACCEPT`.

Эксперимент из проекта — одинаковые правила в разном порядке:

```bash
# ws1 — сначала DROP
iptables -A OUTPUT -p icmp --icmp-type echo-reply -j DROP
iptables -A OUTPUT -p icmp --icmp-type echo-reply -j ACCEPT
# → ping ws1: 100% loss

# ws2 — сначала ACCEPT
iptables -A OUTPUT -p icmp --icmp-type echo-reply -j ACCEPT
iptables -A OUTPUT -p icmp --icmp-type echo-reply -j DROP
# → ping ws2: 0% loss
```

Правила блокируют не входящий ping (`echo-request` в INPUT), а **ответ** на него (`echo-reply` в OUTPUT). Результат для отправителя тот же — ответа нет.

> Правило ниже совпавшего никогда не сработает. В ws2 строка с `DROP` — «мёртвое» правило.

## Скрипт фаервола

```bash
#!/bin/sh
# /etc/firewall.sh
iptables -F     # удалить все правила во всех цепочках таблицы filter
iptables -X     # удалить пользовательские цепочки

iptables -A INPUT -p tcp --dport 22 -j ACCEPT
iptables -A INPUT -p tcp --dport 80 -j ACCEPT
# …
```

```bash
sudo chmod +x /etc/firewall.sh
sudo /etc/firewall.sh
sudo iptables -L -n -v --line-numbers
```

| Флаг `-L` | Значение |
|---|---|
| `-n` | не разрешать IP в имена — быстро |
| `-v` | счётчики пакетов и байт по каждому правилу — видно, какие правила срабатывают |
| `--line-numbers` | номера, чтобы удалить: `iptables -D INPUT 3` |

> Правила iptables живут в памяти ядра и **пропадают после reboot**. Сохранить: пакет `iptables-persistent` (`netfilter-persistent save`) или запуск скрипта из systemd-юнита.

> `iptables -F` не меняет **политики**. Если раньше было `-P INPUT DROP`, после `-F` все входящие отбрасываются — на удалённом сервере так теряют SSH.

## nmap: хост «молчит» на ping, но жив

```bash
nmap 192.168.100.10
# Host is up …
# 22/tcp open ssh
# 80/tcp open http
```

На ws1 ping блокировался, но `nmap` показал `Host is up`. nmap определяет доступность не только по ICMP echo: он отправляет TCP-пакеты на 80 и 443 (SYN/ACK) и ICMP timestamp; в одной сети с целью — ещё и ARP-запрос. Ответ на любой из них = хост жив.

> Блокировка ping не скрывает сервер. Безопасность — это закрытые порты и default deny, а не молчание на ICMP.

| Команда nmap | Что делает |
|---|---|
| `nmap host` | 1000 популярных TCP-портов |
| `nmap -p 22,80,8080 host` | конкретные порты |
| `nmap -sn 10.20.0.0/26` | только обнаружение живых хостов, без сканирования портов |
| `nmap -Pn host` | не проверять «жив ли», сразу сканировать порты |
