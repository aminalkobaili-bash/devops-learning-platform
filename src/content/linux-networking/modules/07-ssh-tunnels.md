## Задача

Apache на ws22 переведён на `Listen localhost:80`: сервис отвечает только самому ws22. Прямое подключение `telnet 10.20.0.20 80` с ws21 → `Connection refused`. Нужно получить к нему доступ, не открывая порт в сеть.

```
# /etc/apache2/ports.conf (ws22)
Listen localhost:80
```

| Адрес Listen | Кто может подключиться |
|---|---|
| `0.0.0.0:80` | все — по любому адресу хоста |
| `localhost:80` / `127.0.0.1:80` | только процессы на этом же хосте |

> Привязка к localhost — стандартный способ закрыть служебный сервис (базу данных, админку) от сети. Доступ к нему дают через SSH-туннель — шифрованный, с аутентификацией по SSH.

## Local forwarding: -L

«Открой порт **у меня**, а соединения на него передавай **через SSH-сервер** на указанный адрес».

```bash
# на ws21
ssh -L 8080:127.0.0.1:80 amuser@10.20.0.20
```

| Часть | Где | Смысл |
|---|---|---|
| `8080` | ws21 (клиент) | локальный порт, который откроет ssh |
| `127.0.0.1:80` | **с точки зрения ws22** | куда SSH-сервер подключится |
| `amuser@10.20.0.20` | — | SSH-сервер, через который идёт туннель |

```bash
# на ws21, во втором терминале
telnet 127.0.0.1 8080     # → Connected: это Apache ws22
```

> `127.0.0.1` в `-L 8080:127.0.0.1:80` — это localhost **сервера** ws22, а не клиента. Адрес разрешается на той стороне туннеля.

## Remote forwarding: -R

«Открой порт **на SSH-сервере**, а соединения на него передавай **назад через туннель** на указанный адрес с моей стороны».

```bash
# на ws22
ssh -R 8080:127.0.0.1:80 amuser@10.10.0.2
```

| Часть | Где | Смысл |
|---|---|---|
| `8080` | ws11 (SSH-сервер) | порт, который откроется на ws11 |
| `127.0.0.1:80` | **с точки зрения ws22** (клиента) | куда пойдёт соединение |
| `amuser@10.10.0.2` | — | ws11 |

```bash
# на ws11
telnet 127.0.0.1 8080     # → Connected: Apache ws22
```

Зачем: опубликовать сервис из закрытой сети, когда к ней нельзя подключиться снаружи, но изнутри можно подключиться наружу. ws22 сама открывает SSH-соединение к ws11 — входящие соединения в сеть ws22 не нужны.

## Сравнение

| | `-L` (local) | `-R` (remote) |
|---|---|---|
| Где открывается порт | на клиенте (откуда запускаешь ssh) | на SSH-сервере |
| Куда ведёт | в сеть SSH-сервера | в сеть клиента |
| Типичный случай | дойти до базы за bastion-хостом | показать локальный сервис снаружи |

> По умолчанию порт туннеля слушает только `127.0.0.1`. Открыть его для других машин: `-L 0.0.0.0:8080:…` или для `-R` — `GatewayPorts yes` в `sshd_config` сервера.

## Полезные флаги

| Флаг | Значение |
|---|---|
| `-N` | не запускать команду на сервере — только туннель |
| `-f` | уйти в фон после подключения |
| `-D 1080` | dynamic forwarding: SOCKS-прокси через сервер |
| `-J user@bastion` | подключиться через промежуточный хост (jump host) |

```bash
ssh -N -f -L 5432:127.0.0.1:5432 user@db-server   # туннель к PostgreSQL в фоне
```

## Ошибки из проекта

**`-l` вместо `-L`.** Команда была набрана как `ssh -l 8080:127.0.0.1:80 …`. Строчная `-l` — имя пользователя (`-l amuser` = `amuser@`), и SSH запросил пароль для пользователя `8080:127.0.0.1:80`. Ключи `ssh` чувствительны к регистру.

**`Could not request local forwarding`.** Порт 8080 на ws21 уже был занят предыдущей сессией туннеля. SSH-подключение установилось, но туннель — нет. Проверить, кто занял порт:

```bash
sudo ss -tlnp | grep 8080
```

Итог — туннель подтверждён: `telnet 127.0.0.1 8080` на ws21 → `Connected` при том, что прямое подключение к ws22:80 отклоняется.
